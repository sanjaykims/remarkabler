### Hard-won rules around embedding backfill

- **Voyage-3 caps: 32K tokens per single input, ~120K tokens per request,
  1000 inputs per request.** Free tier additionally caps at 10K TPM /
  3 RPM. We chunk batches by *estimated* token count (`chars / 2` for
  Korean-heavy text — `chars / 3` undercounts), not by row count, with
  a 100K-token-per-request budget.
- **`embedBatch` returns `null` silently on Voyage errors.** Use
  `embedBatchOrThrow` in the manual backfill path so the user sees the
  real error (429 vs 400 vs auth) instead of staring at a stalled count.
- **Per-page fallback is required.** When a batch fails, fall back to
  embedding one page at a time so one bad page can't kill the rest.
  Track skipped IDs to avoid retrying the same broken page in a loop.
- **`ORDER BY LENGTH(ocr_text) ASC` in the backfill SELECT.** Discipline
  notebook pages (GitHub markdown files) are 5-15K chars each; without
  ordering, they cluster together and blow the per-request token cap.
  Smallest-first guarantees big pages get tried alone where per-page
  fallback handles them.
- **`decodeEmbedding` validates BLOB length** and returns null on
  malformed rows. Without this, a corrupt embedding would silently
  zero out every cosine similarity comparison against it.

## OCR stays on Opus — validated against Sonnet

Don't propose switching the OCR model to Sonnet for this user. The
question came up; we tested it properly; the answer is no.

### How we tested

Spawned 4 agents (2× Opus, 2× Sonnet) on each of 3 real diary pages.
Same image, same prompt, same instructions, just different models.
Compared every word.

### What we found

| Page type | Sonnet performance |
|---|---|
| Clean structured list (numbered items, English brand names mixed in) | **Matches Opus** — only formatting differences |
| Dense Korean narrative | **3-4 meaning-changing errors per page**, consistent across runs |

Sonnet's failures on dense Korean handwriting:
- "엘지" (LG) → "멜지" (non-word) — both runs
- "족발집" (pig's feet restaurant) → "조반 집" / "종반 집" (gibberish) — both runs
- "실상은" (in reality) → "싫고" / "싫없고" (meaning shifts to "hated") — both runs
- "줄다리기" (tug-of-war) → "줄다니기" / "돌아다니기" — both runs
- "뻐근함" (stiffness) → "빠르게 힘이" / "빠르고 힘이" — both runs

These aren't random noise. Sonnet **consistently** misreads the same
words the same wrong way every run. Two runs of Sonnet won't catch
what one run misses.

Opus errors: 0-2 minor per page, never meaning-changing.

### Why this matters

The user's diary is mostly dense Korean narrative. Sonnet's errors
would silently drift their evolving Memory profile away from who they
actually are. That's the opposite of what this app exists to do.

### What's still possible

If the user ever asks about lowering OCR cost again:

1. **Glossary injection** in the OCR prompt (extract recurring proper
   nouns from existing Opus transcriptions, inject as "common terms in
   this diary include...") — could plausibly fix proper-noun errors
   (LG, places). Not tested yet — the user chose to stay on Opus
   before we ran this experiment. **Worth trying in a future session
   if cost optimization comes up again.**
2. Fine-tuning Claude is not possible. Anthropic doesn't offer it.
3. Few-shot example pages in the prompt — high token cost, uncertain
   gains.

## Code review pass (PR #7 — merged 2026-06-04)

10 parallel agents (security, API hygiene, DB, error handling, types,
Claude integration, UI/UX, dead code, cost/perf, mobile/PWA) audited
the codebase. The top 10 fixes landed in `main`:

- **Chat system prompt cache split.** Was one block containing static
  instructions + dynamic profile + dynamic locations, so any
  profile/location change blew the entire cache. Now two blocks; the
  static one has `cache_control`, the dynamic one doesn't.
- **`backfillTitles` was firing Opus on every Insights page load.**
  Throttled to 1×/5min, capped to 3 per run, switched to Sonnet.
- **`runMaintenanceSweep` timestamp now persisted in settings.**
  Previously in-memory only; Railway cold-starts refired the entire
  cascade (embedding backfills, daily summaries, weekly insight) on
  every restart.
- **Chat fallback model loop fix.** Was gated by `iter === 0`, so a
  mid-tool-loop 529 surfaced as an error. Now falls back on any iter
  and logs the switch.
- **15 API routes got `export const dynamic = "force-dynamic"`.**
  Stale data risk gone.
- **`/api/chat` `maxDuration` bumped 60 → 300.** Complex tool chains
  no longer cut off mid-stream.
- **`COALESCE(SUM(...), 0)` in `lib/usage.ts`** so the Cost tab doesn't
  crash on empty days/months.
- **`decodeEmbedding` validates BLOB length** and returns null.
- **`console.warn` / `console.error` on silent catches** in
  `processNotebook`, `semanticSearch`, post-OCR profile fold, chat
  fallback. Railway logs now show what's failing.
- **Notebooks page**: loading skeleton + Delete busy-lock + error
  surface. Was fire-and-forget with no feedback.
- **Insights "Generate"**: double-tap guard.

## Deferred for future sessions

Real findings from the audit that didn't make it into PR #7 because
they need bigger thought:

1. **Brute-force protection on the passcode endpoint** (security agent,
   HIGH). `/api/auth` POST with `action: "passcode"` is rate-unbounded.
   Track failed attempts per IP in `settings` and 429 with exponential
   backoff after N failures.
2. **Per-session activity tracking** (security agent, HIGH). The 24h
   inactivity timeout currently uses a single global `last_activity_at`
   in `settings`, so a stolen cookie keeps refreshing as long as the
   real owner is active anywhere. Bind to a session ID in the token.
3. **Token revocation list** (security agent, HIGH). HMAC session
   tokens are stateless — `logout` only clears the cookie, doesn't
   invalidate the token. Anyone with the captured token can replay it
   for up to 7 days. Add an "issued-after" epoch in settings, bump on
   logout.
4. **OCR routing by PDF size** (cost agent, $20-80/mo potential).
   `ocrNotebookPdf` always uses `modelMain` (Opus) regardless of page
   count. Now off the table specifically for this user (Opus is the
   right call — see above), but the routing infrastructure could still
   reduce cost for short pages without hurting quality. Low priority.
5. **Backup failure tracking** (cost agent). `runBackup` doesn't set
   `backup_last_at` when it fails, so `maybeRunWeeklyBackup` retries on
   every sweep tick — turning a weekly backup into a 5-minute-cadence
   retry of a 100MB+ upload if the GitHub Contents API rejects it
   (>100MB single-file limit). Set last-at on failure with backoff.
6. **iOS PWA polish** (mobile agent). Web Share Target doesn't exist
   on iOS Safari; voice input doesn't exist; `pagehide` fires in more
   contexts (URL bar collapse, keyboard show) so 0-second AutoLock
   may re-lock mid-typing on iOS. The user uses Android primarily so
   none of this is urgent.
