# Session log — 2026-07-05

A reference for future Claude sessions on what was decided and validated in
this session, so the same ground doesn't get re-covered. Theme: making the
diary export drive a live **Obsidian graph** of the user's life, plus a
duplicate-notebook cleanup.

## Duplicate-notebook detection (shipped, PR #103)

- Old notebooks (Dropbox-ingested via `dropbox_file_id`, or manually
  uploaded with neither origin id) can cover the same diary dates as a
  notebook later imported/synced from the reMarkable cloud
  (`remarkable_doc_id`). Both copies then feed chat/`/mind`/diary export.
- `lib/notebookDedup.ts` (pure: `classifyDuplicate`, `buildCloudCoverage`,
  `buildCandidate`) + `lib/notebookDedupDb.ts` (`findDuplicateCandidates`,
  one query, no N+1). "Possible duplicates" section on `/notebooks`,
  manual delete only, reusing the existing `remove()` pattern.
- **"old" = `remarkable_doc_id IS NULL`** (not just `dropbox_file_id NOT
  NULL`) so a manually-uploaded notebook duplicated by a cloud import is
  also flagged. Discipline notebook excluded explicitly by id.
- **No `notebooks.status` gate** — `ocr_text IS NOT NULL AND != ''` is the
  sole gate, matching every other DB reader. A cloud notebook mid-resync
  flips to `status='processing'` while its already-synced pages still have
  real `ocr_text`; gating on status would cause spurious full→partial flips.
- v1 scope limit (intentional): only old-vs-cloud detected, not old-vs-old.

## Obsidian graph integration (the big one)

Goal: the per-day Dropbox diary files (`/Remarkabler/diary/YYYY-MM-DD.md`,
already Obsidian-native with `[[wikilinks]]`) should render as a live graph
of people/places/projects in the user's Obsidian vault. Validated
end-to-end on the user's phone — the graph now shows their whole network
(Korean + English entity names, all clickable).

### Remotely Save uses a hidden Dropbox APP FOLDER — this is the load-bearing gotcha

- The user chose **Remotely Save** (Obsidian community plugin) to sync
  Dropbox → vault. **Its Dropbox integration only reads/writes
  `/Apps/remotely-save/<vaultName>/`** — a scoped app folder, NOT arbitrary
  Dropbox paths. It also **rejects `/` in its "remote base directory"**
  field, so you can't point it at a nested path like `Remarkabler/diary`.
- Therefore Remotely Save can NEVER see Remarkabler's real
  `/Remarkabler/diary` export. Two ways to bridge, we took option B:
  - **A (rejected):** FolderSync (full-Dropbox app) reads the real folder →
    local vault. Robust, but another app to set up.
  - **B (shipped):** point Remarkabler's *export* at the app folder Remotely
    Save already watches. Remarkabler's Dropbox app has full (root) write
    access, so it can write into `/Apps/remotely-save/Diary`.
- **The user's vault is named `Diary`**, so their working export folder is
  **`/Apps/remotely-save/Diary`**.

### Editable Dropbox export folder (shipped, PR #103)

- The export destination was a `dropbox_export_folder` setting with no UI.
  Added an editable **"Destination folder"** field on `/memory` +
  `setDropboxExportFolder()` (normalizes: leading slash, no trailing slash,
  empty → default) + a `{ folder }` field on `POST /api/dropbox/export`.
  Saving with export on runs one export immediately.

### Entity stub notes — clickable graph nodes (shipped, PR #104)

- The day files' `[[Jin]]`/`[[Seoul]]` links pointed at notes that didn't
  exist → Obsidian showed them as "unresolved" nodes you couldn't open.
- Now the Dropbox export also writes **one stub note per entity**:
  `People/<name>.md`, `Places/<name>.md`, `Projects/<name>.md`, each with
  `type:` frontmatter and `[[YYYY-MM-DD]]` links back to the days it
  appears. Pure `buildEntityStubFiles`/`entityStubFileName` +
  DB-backed `renderEntityStubFiles`/`affectedEntityStubFileNames`. Merged
  into `maybeExportDiaryToDropbox` (incremental per notebook, full on a
  whole-vault sync). Obsidian's backlinks panel also derives the day list
  live, so a slightly stale stub still reads fine.

### Codex #104 — stub filename MUST equal the wikilink text (shipped)

- A name with a path char (e.g. `Dr/Kim: MD`) rendered `[[Dr/Kim: MD]]` in
  the day file but was saved as `People/Dr Kim MD.md` → mismatched basename
  → stays unresolved, defeating the stubs. Fix: **`sanitizeEntityName` now
  also collapses `/ \ : * ? " < >` to spaces**, so the wikilink text and the
  stub filename derive from ONE normalization and always match. Keep all
  three consumers (day-file wikilink, YAML frontmatter, stub basename)
  routed through `sanitizeEntityName`.

### ByteString bug — non-ASCII (Korean) paths broke uploads (shipped, PR #105)

- **The big live failure.** Enabling stubs failed **124 of 215 uploads**
  with "Cannot convert argument to a ByteString ... value 54844 > 255".
  The `Dropbox-API-Arg` HTTP header carries the file path and must be
  ASCII-only. Date-named day files (ASCII) uploaded fine; **Korean entity
  names in the stub paths (`People/김…​.md`, U+AE40) can't go in a header.**
- Fix: **`dropboxApiArg()`** `\uXXXX`-escapes every non-ASCII char (the form
  Dropbox documents), used for both the upload AND download content
  endpoints. **Do not `JSON.stringify` a path straight into `Dropbox-API-Arg`
  — always route through `dropboxApiArg`.** This was latent for any
  non-ASCII path; Korean stub names just exposed it. Regression test in
  `test/dropboxApiArg.test.ts`.

### End-to-end verified

- After the ByteString fix deployed, "Export now" wrote all files (no red
  error — it backgrounds the full sync, so the UI shows "Syncing … in the
  background" rather than a count; absence of the error is the success
  signal). Remotely Save synced them in. The user's Graph view now shows
  the full network with clickable People/Places/Projects nodes.
