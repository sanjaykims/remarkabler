# Session log — 2026-08-25

A reference for future sessions on what was decided and validated, so the same
ground isn't re-covered. Theme: **independently verifying an AI-authored
remediation branch, then shipping it** — plus closing an authentication bypass
that turned out to be live in production and pre-existing.

The single most useful thing recorded here is not any individual fix. It is
that **the review loop caught what each side missed**, in both directions, and
what that implies for how this repo should ship security work.

## Starting point

`codex/full-review-remediation` (commit `030a7f3`) — one commit, 115 files,
bundling a Next 14→16 / React 18→19 upgrade with quarantine, OAuth, session,
and container work. Its own session log stated that local verification could
not cover a Railway-mounted `/data` volume or real API credentials.

## What independent verification found

Six reviewers were run over disjoint areas of the diff. Two **criticals** came
out of it, neither of which the authoring side had flagged.

### 1. Interrupted reMarkable syncs destroyed diary pages (introduced)

Boot recovery classified an interrupted job by asking whether
`DATA_DIR/files/<id>/notebook.pdf` existed, on the stated premise that
"incremental reMarkable sync also uses `processing` but has no notebook PDF".

**That premise is false.** `lib/remarkableSync.ts` writes `notebook.pdf` after
every content change so the notebook stays viewable, so a synced notebook has
one permanently. Every sync interrupted by a restart was therefore re-queued as
a whole-PDF OCR job, whose first act is `DELETE FROM pages` — destroying
per-tablet-page rows and, via `ON DELETE CASCADE`, `entry_analysis` and
`entry_entities` with them.

For pages since deleted on the tablet, those rows were the **only surviving
copy** (the append-only invariant), so the loss was unrecoverable. The trigger
was ordinary use: Railway restarts on every push to `main`, and syncs are long.

The fix asks the question that actually matters — could re-running whole-PDF
OCR destroy anything? — and never re-queues a notebook holding per-tablet-page
rows. The logic moved out of `db()` into an exported
`recoverInterruptedNotebooks()` **because inline in a connection initializer it
was untestable, which is why the bug shipped at all.**

### 2. Unauthenticated passkey enrollment (pre-existing, live)

`login-options` is ungated by necessity — an unauthenticated visitor must be
able to start a passkey login. It issued a challenge cookie, and
`register-verify` accepted whatever sat in that same cookie with no passcode
check. The passcode gate on `register-options` therefore protected nothing.

Registration uses `attestationType: "none"`, so no cryptography had to be
broken. Anyone who could reach the deployment could obtain a session **and** a
permanently registered passkey that survives passcode rotation and "Lock all".

This predated all of the remediation work. It had been exposed for as long as
the app had a passcode set.

## The part worth remembering: two fixes, two misses

**The first fix (#164) was incomplete, and an automated review caught it.**
Separating the two challenge cookies stopped a login-issued challenge being
replayed into `register-verify` — but the cookie is client-supplied. `httpOnly`
protects a victim's browser from XSS; it does nothing against a direct caller
sending `Cookie: fc_reg_challenge=<anything>` from curl. Nothing recorded which
challenges the server had issued, so an attacker could invent one outright.
Confirmed against deployed code: a made-up string returned a real session.

**The second fix (#165) introduced a resource regression, which the same review
caught.** Binding challenges server-side meant the ungated `login-options` now
wrote a row per call. TTL cleanup only reaps rows older than five minutes, so a
sustained flood could keep an arbitrarily large set of *fresh* rows and WAL
churn on `/data` without ever passing the app lock. Fixed with a hard row cap,
evicting newest-first so a legitimate in-flight login cannot be displaced.

Both were real. Neither was caught by the tests, the type checker, or the
author. **Both were caught by review.**

## Decisions

- **Separate cookie names are not a sufficient control for a client-supplied
  value.** The server must record what it issued. Recorded as a hard rule so
  this area is not half-fixed a third time.
- **The passcode limiter needs two buckets, not one.** Per-source for fairness,
  plus a global floor so that a wrong `X-Forwarded-For` trust assumption
  degrades the limiter to "slow" rather than "unlimited". A global-only design
  shipped once (one attacker could lock the owner out); per-source-only shipped
  once (no ceiling at all). Keep the pair.
- **`skipped: "in-flight"` means an export did not happen.** Never record it as
  a completed repair — the same "treated didn't-happen as done" mistake that
  caused the original export race.
- **Split a change by what can be verified before merging, not by subject
  matter.** See below.
- **Do not publish exploit detail for a live vulnerability in a public repo.**
  See "Mistakes" below.

## The split, and why the obvious cut was wrong

The first instinct was to separate *security fixes* from the *framework
upgrade*. That was wrong twice over: the remediation was a single commit
bundling both, and the security code depended on the async-`cookies()`
migration Next 16 brought, so separating them meant re-implementing the work on
the old base.

The correct cut was **what can be verified before merging vs. what cannot**:

| Verified how | |
|---|---|
| Next 16 / React 19 / all security fixes | built, 708 tests, server booted, routes smoke-tested |
| **Dockerfile + entrypoint** | **never built — only a deploy can answer it** |

So `Dockerfile` and `docker/entrypoint.sh` shipped alone (#167). A container
failure became a two-file revert instead of one that would take 117 files of
application fixes down with it.

**Generalisation for future work:** the framework upgrade *felt* like the risky
half and was not — it had been exercised end to end. The two-file container
change *felt* trivial and was the only genuinely unverifiable part.

## Verification practice used throughout

Every fix with a regression test was **confirmed to fail against the pre-fix
code** before being accepted. This caught two tests that would otherwise have
passed either way, and one that passed *for the wrong reason*
(`test/pendingShares.test.ts` set `x-real-ip` while `clientIp` read only
`x-forwarded-for`, so its source silently became `"unknown"`).

Two merges auto-merged `lib/auth.ts` and `app/api/auth/route.ts` **with no
conflict** and were checked anyway. The first was **semantically broken despite
being textually clean** — it still referenced a removed constant in a new
`logout-all` handler. Git saw no conflict because the two sides touched
different lines.

**Rule of thumb this produced: a clean auto-merge in a file both sides rewrote
is not evidence of correctness. Verify the merged behaviour, not the merge
exit code.**

## Mistakes made in this session

Recorded because the corrections matter more than the fixes.

1. **Published exploit detail for a live vulnerability in a public repository.**
   PR #164's body and commit message described the bypass in full, including a
   working payload, while the fix was still incomplete and the app still
   exposed. Standard practice is to fix quietly, then disclose. PR bodies were
   sanitised afterwards; **commit messages are permanent** and were left rather
   than rewriting published history.
2. **Claimed a vulnerability was closed when it was not.** #164 was merged and
   reported as complete. The correction came from an automated review, not from
   this side.
3. **Mischaracterised the dependency audit** as "transitive postcss" when it
   spanned four distinct chains including a direct `next` advisory. Corrected
   after being challenged.
4. **Overstated a claim** that a missing session cookie on `/share` was
   "guaranteed". The logout is best-effort. The conclusion survived via a
   different mechanism (`sameSite: "lax"`), but the original reasoning was too
   strong.
